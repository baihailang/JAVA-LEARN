## jvm 内存分析
![[Pasted image 20260826205914.png]]


`Math.java` 被编译成 `.class`，类加载子系统将其放入**方法区**；随后 `main` 线程启动，在**虚拟机栈**中依次压入 `main` 和 `compute` 栈帧，`compute` 栈帧通过**局部变量表**存储 `a=1，b=2`，并通过**程序计数器=4**定位当前执行位置，**执行引擎**负责驱动这一切计算，计算结果可能返回给 `main`



**1、堆（Heap）：** 这是Java内存管理中最大的一块，被所有线程共享。在堆中主要存放对象实例和数组。

**2、栈（Stack）：** 每个线程运行时都会创建一个栈，用于存放局部变量、操作数栈、动态链接和方法出口等。栈的生命周期和线程同步。

**3、方法区（Method Area）：** 同样被所有线程共享，用于存储已被虚拟机加载的类信息、常量、静态变量等数据。

**4、本地方法栈（Native Method Stack）：** 专门用于处理本地native方法的调用。

此外，Java内存模型还包括程序计数器等组件，共同构成了Java的运行时数据区。

### 1. 年轻代的内部结构（从左到右）

图中明确标出了年轻代的三个区域及其**默认内存比例**（可通过 `-XX:SurvivorRatio` 调整）：

- **Eden区（伊甸园）**：占年轻代的 **8/10**（80%）。绝大多数新创建的对象都会在这里分配内存。
    
- **S0（Survivor 0）**：占 **1/10**（10%）。
    
- **ST（这里应为S1或To Survivor）**：占 **1/10**（10%）。
    

> **核心机制**：S0和S1（两个Survivor区）在任意时刻，**必有一个是空的**（作为“To”区），用来存放下一次Minor GC后存活下来的对象。

### 2. Minor GC 的执行流程（复制算法）

图中的 **`minor gc`** 箭头指向了对象在年轻代内部的流动方向，流程如下：

1. **新对象**总是先分配到 **Eden** 区。
    
2. 当Eden区空间不足时，触发 **Minor GC**（也称Young GC）。
    
3. JVM采用**标记-复制**算法：将 **Eden区** 和 **当前非空的Survivor区（假设为S0）** 中**存活**的对象，一次性复制到 **另一个空的Survivor区（ST/S1）**。
    
4. 复制完成后，**清空** Eden区和原来的S0区。
    
5. 此时，**S1** 变成非空（存放存活对象），而 **S0** 变成空区，等待下一次Minor GC时作为接收区。**两个Survivor区（S0和S1）的角色就此互换**。
    

### 3. 关键数值“15”的含义（晋升阈值）

图中在Survivor区标注的 **“15”**，代表**对象年龄阈值**（即 `-XX:MaxTenuringThreshold` 默认值）。

- 每经历一次Minor GC且存活下来，对象的“年龄”就 **+1**。
    
- 当对象的年龄达到 **15** 时，它就不再适合待在年轻代了，会在下一次Minor GC时被**晋升（Promoted）** 到**老年代（Old Generation）**。
    

### 4. Full GC 和 OOM 的触发链条

图中的 **`full gc`** 和 **`OOM`** 连接了年轻代与整个堆的“生死线”：

- 当大量对象在Minor GC后存活，导致Survivor区放不下时，**多余的对象会直接提前晋升到老年代**。
    
- 如果老年代空间也不足，就会触发 **Full GC**（对整个堆和方法区进行全局回收）。
    
- 如果 **Full GC 执行后**，老年代依然无法容纳晋升进来的对象，或者堆内存整体无法满足新对象的分配需求，JVM最终就会抛出 **OOM（OutOfMemoryError）**
**一句话总结图中的逻辑流向**：  
对象先在 **Eden (8/10)** 出生，经历 **Minor GC** 后，存活者借助 **复制算法** 在 **S0** 和 **ST/S1 (各1/10)** 之间反复拷贝并累加年龄，达到 **15岁** 后晋升老年代；若整个过程中老年代也满了，就会触发 **Full GC**，最终无法释放空间时抛出 **OOM**。


# Arthas 常用命令速查手册

Arthas 是阿里巴巴开源的 Java 诊断工具，能在不重启应用的情况下实时监控、排查线上问题。以下为最常用命令的分类说明、作用及典型用法示例。

---

## 1. 基础命令

| 命令 | 作用 | 示例 |
|------|------|------|
| `help` | 查看所有命令列表或指定命令的详细用法 | `help`<br>`help dashboard` |
| `dashboard` | 实时展示 CPU、内存、线程、GC 等核心指标 | `dashboard -i 2000`（每 2 秒刷新） |
| `thread` | 查看线程状态、CPU 占比、堆栈，定位死锁/阻塞 | `thread -n 5`（最忙 5 个线程）<br>`thread -b`（检测死锁） |
| `jvm` | 查看当前 JVM 的详细信息（内存区域、GC 策略等） | `jvm` |
| `quit` / `exit` | 退出当前 Arthas 会话，不影响目标应用 | `quit` |
| `reset` | 重置被 Arthas 增强过的类，还原为原始状态 | `reset`（重置所有）<br>`reset *Service` |

# JVM 内存分配与调优指南

JVM 调优不是简单的“加内存”或“改参数”，它需要结合业务特点、系统资源和监控数据，有策略地进行。

---

## 1. 调优目标：在“三难困境”中找平衡

JVM 调优的本质，是在以下三个目标之间寻找最适合你业务的平衡点：

| 目标                           | 说明                       | 适用场景                          |
| :--------------------------- | :----------------------- | :---------------------------- |
| **低延迟 (Low Latency)**        | 追求更短的 GC 停顿时间（如 < 100ms） | 对响应时间敏感的**实时交互**场景（电商秒杀、支付交易） |
| **高吞吐量 (High Throughput)**   | 追求单位时间内完成更多任务            | **后台计算**场景（批处理、报表分析）          |
| **内存高效 (Memory Efficiency)** | 合理利用内存，避免浪费并防止内存溢出（OOM）  | 资源受限环境                        |
|                              |                          |                               |

> **注意**：通常，低延迟和高吞吐量难以两全，需要根据业务确定优先级。

---

## 2. 核心战场：JVM 内存模型概览

调参前，先了解 JVM 内存的主要区域：

| 区域                                   | 说明                           | 是否调优重点 |
| :----------------------------------- | :--------------------------- | :----: |
| **堆内存 (Heap)**                       | 存储所有**对象实例**。调优的核心区域         |   ✅    |
| **元空间 (Metaspace)**                  | 存储**类信息**、常量池等（Java 8 取代永久代） |   ✅    |
| **虚拟机栈 (VM Stack)**                  | 每个线程私有，存储方法调用的**栈帧**         | 一般无需调优 |
| **本地方法栈 (Native Method Stack)**      | 为 `native` 方法服务              | 一般无需调优 |
| **程序计数器 (Program Counter Register)** | 记录线程执行位置                     |  无需调优  |

---

## 3. 调优工具箱：核心参数详解

### 3.1 堆内存大小：最重要的基础参数

| 参数 | 说明 | 建议 |
| :--- | :--- | :--- |
| **`-Xms`** | 设置堆内存的**初始**大小 | **建议与 `-Xmx` 设置为相同值**，避免 JVM 运行时动态调整堆大小带来的性能开销 |
| **`-Xmx`** | 设置堆内存的**最大**大小 | 生产环境务必显式设置 |
| **`-Xmn`** | 设置**年轻代**（Young Generation）的大小 | 官方推荐为整个堆大小的 **3/8** |

> **关于堆大小的建议**：
> - **总量规划**：通常建议 JVM 堆内存占服务器总内存的 **60% ~ 80%**。例如，一台 4G 内存的服务器，可以给 JVM 分配 **3G**（`-Xms3072m -Xmx3072m`）。
> - **不要过大**：堆内存过大会导致一次 Full GC 时间过长，影响服务可用性。

**参考值（需结合压测调整）**：

| 服务器配置  | `-Xms` / `-Xmx` | `-Xmn` (年轻代) | `-XX:MetaspaceSize` |
| :----- | :-------------- | :----------- | :------------------ |
| 1C 2G  | 1G              | 500M         | 128M                |
| 2C 4G  | 2560M           | 1200M        | 256M                |
| 4C 8G  | 4G              | 2G           | 384M                |
| 8C 16G | 10G             | 5G           | 512M                |

### 3.2 分代比例：精细化管理内存

年轻代和老年代的比例，直接影响着 Minor GC 和 Full GC 的频率。

| 参数 | 说明 | 默认值 | 示例 |
| :--- | :--- | :--- | :--- |
| **`-XX:NewRatio`** | 老年代 : 年轻代的**比值** | 2（老年代:年轻代 = 2:1，年轻代占堆的 1/3） | `-XX:NewRatio=4`（年轻代占堆的 1/5） |
| **`-XX:SurvivorRatio`** | Eden 区 : 一个 Survivor 区的**比值** | 8（Eden:S0:S1 = 8:1:1） | `-XX:SurvivorRatio=4`（Eden:S0:S1 = 4:1:1） |
| **`-XX:MaxTenuringThreshold`** | 对象在年轻代经历多少次 Minor GC 后晋升到老年代 | 15 (Parallel GC) / 6 (CMS GC) | 值越小，对象越早晋升到老年代 |

### 3.3 非堆内存与线程栈

| 参数 | 说明 | 建议 |
| :--- | :--- | :--- |
| **`-XX:MetaspaceSize`** | 元空间的**初始**大小 | 根据应用加载的类数量设置，避免启动时频繁扩容 |
| **`-XX:MaxMetaspaceSize`** | 元空间的**最大**大小 | **建议设置上限**，防止因类加载问题导致元空间无限膨胀 |
| **`-Xss`** | 设置每个**线程栈**的大小 | JDK 8+ 默认为 1M。如果应用线程数非常多，可适当减小（如 256k） |

---

## 4. 垃圾收集器（GC）选型

选择合适的 GC 是调优的关键一步。

| 收集器 | 适用场景 | 关键参数 |
| :--- | :--- | :--- |
| **G1 (`-XX:+UseG1GC`)** | **多核大内存**（堆 > 6GB），追求**低延迟**和**可预测停顿**的**通用场景** | `-XX:MaxGCPauseMillis=200`（目标停顿时间） |
| **Parallel (`-XX:+UseParallelGC`)** | **多核 CPU**，追求**高吞吐量**的后台任务，允许较长 GC 停顿 | JVM 8 的默认 GC |
| **CMS (`-XX:+UseConcMarkSweepGC`)** | **多核 CPU**，对**延迟**要求高，但内存小于 4G 的场景 | 已在 Java 9 中标记为废弃 |
| **Serial (`-XX:+UseSerialGC`)** | 单核 CPU 或内存小于 100M 的**极小应用** | - |

---

## 5. 调优实战流程：一套可复用的方法

1. **明确目标**：确定业务是优先低延迟还是高吞吐量。
2. **建立基准**：在测试环境用**默认参数**运行，通过监控工具记录 GC 频率、停顿时间等作为“基线”。
3. **设定参数**：根据服务器内存设置 `-Xms` 和 `-Xmx`，并选择一个 GC（推荐 G1）。
4. **压力测试**：使用 JMeter 等工具模拟真实流量，观察应用表现。
5. **监控与分析**：利用工具观察 GC 日志和内存使用，找出问题。
6. **微调参数**：根据分析结果，调整分代比例、GC 参数等。
7. **重复验证**：重复压测和调整，直到达到目标。
8. **灰度发布**：在生产环境先对少量机器应用新参数，观察稳定后全量。

---
